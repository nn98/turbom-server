# 경매정보 연동 설계 — 소스 조사 및 접근 방식 기록

**Date:** 2026-07-18
**Status:** Approved (방향만 — 실제 엔드포인트 역공학은 미완료, 구현 계획 이전 단계)

---

## 문제

기존 서비스는 "지번 단위 자리의 개업–폐업 이력"만 다룬다. 경매정보(법원경매로 넘어간 이력·감정가·낙찰가 등)를
같은 자리(PNU)에 곁들이면 예비창업자의 입지 실사에 신호가 하나 더 붙는다("이 자리가 경매로 나온 적 있는지,
감정가/낙찰가는 얼마였는지"). 이 문서는 실제 설계·구현 전에 **어디서 데이터를 받아올 수 있는지 조사**하고,
검토한 여러 접근 방식을 트레이드오프째로 기록한다 — 하나를 골라 시도했다가 막히면 여기 남은 다른 옵션을
바로 꺼내 쓸 수 있게 하는 게 이 문서의 핵심 목적이다.

## 조사 결과

### 데이터 소스 지형

| 소스 | 성격 | 비고 |
|---|---|---|
| **대법원 법원경매정보(courtauction.go.kr)** | 원천. 모든 상업 서비스가 여기서 파생 | 공식 REST API 없음. `robots.txt` 자체가 없음(404) — 크롤링을 기술적으로 막아두진 않았지만 명시적 허용도 아님. 이용약관에서 크롤링 관련 명문 조항은 검색으로 못 찾음(불확실, 확정 아님) |
| **굿옥션 → 현재 "옥션원"(auction1.co.kr)** | 원천에 사진·현장조사·등기부분석을 얹은 B2C 유료 구독 서비스 | 개발자 대상 API 상품 없음. 리브랜딩된 지 얼마 안 됨(구옥션 시절 이름으로 검색해도 옥션원이 나옴) |
| **지지옥션(ggi.co.kr), 태인, 탱크옥션, 두인경매 등** | 옥션원과 동일 성격의 경쟁 서비스들 | 전부 자체 크롤러 기반으로 추정(관련 특허 검색 결과 확인 — "경매 데이터 자동 크롤링" 특허 존재). 공식 API 없음 |
| **CODEF(developer.codef.io)** | 법원경매정보를 이미 상품화한 유료 데이터 중계 API | 스크래핑을 CODEF가 대신 떠안는 구조(마이데이터/스크래핑 대행 라이선스). 정확한 가격·필드는 페이지가 JS 렌더링이라 직접 못 읽음 — 계약 전 별도 확인 필요 |
| **인터넷등기소 등기정보광장(data.iros.go.kr)** | 등기부등본 관련 공식 오픈데이터 포털 | 경매 자체가 아니라 인접 데이터(권리분석에 후속으로 쓸 수 있음). 이번 스코프 밖 |

### 기술적 발견 — courtauction.go.kr은 WebSquare 기반

`https://www.courtauction.go.kr/pgj/index.on?w2xPath=/pgj/ui/pgj100/PGJ157M00.xml` 같은 URL 패턴은
**WebSquare**(전자정부 표준프레임워크의 XML 기반 클라이언트 렌더링 엔진)의 시그니처다. 실제로 `WebFetch`로
접근해보니 빈 콘텐츠만 반환됨(JS 실행 없이는 데이터가 안 보임) — 즉 이 프로젝트가 지금까지 다뤄온 성남시
인허가 CSV(정적 다운로드 파일)와는 완전히 다른 난이도다. 단순 HTML 파싱(Jsoup류)으로는 못 긁고, 헤드리스
브라우저로 렌더링하거나 WebSquare가 내부적으로 호출하는 백엔드 AJAX 엔드포인트를 역공학해야 한다.

## 검토한 접근 방식 (전부 기록 — 하나 실패하면 다음으로 전환)

| # | 방식 | 난이도/비용 | 리스크 | 상태 |
|---|---|---|---|---|
| **A** | CODEF 유료 API 계약 | 낮음(계약만 하면 끝, 유지보수 CODEF 책임) | 비용 미확정, 계약 리드타임 | 미시도 — B2 실패 시 폴백 |
| **B1** | 헤드리스 브라우저(Playwright 등)로 WebSquare 페이지 직접 렌더링·파싱 | 높음(개발+지속 유지보수, UI 변경마다 깨짐) | 가장 무거움, 이 프로젝트 규모(자체호스팅 EC2 1대)에 부담 | 미시도 — B2가 막히면 다음 후보 |
| **B2** | 브라우저 개발자도구로 실제 검색 시 나가는 AJAX 요청(엔드포인트·파라미터·응답 포맷)을 분석해 Java `RestClient`로 재현 | 중간(초기 조사 비용 큼, 런타임은 가벼움 — 헤드리스 브라우저 불필요) | 비공식 API라 문서 없이 예고 없이 바뀔 수 있음. 실제 요청 캡처가 아직 안 됨(이 문서 작성 시점 기준 미완료) | **채택 — 다음 세션에서 착수** |
| **C** | 스키마·DTO·프론트 목업만 먼저 설계, 실연동은 보류(`marketInfo`의 `isPlaceholder:true` 패턴 재사용) | 최저 | 실데이터 없음, 실연동 착수 시점 불확실 | 병행 가능(B2와 동시에 스키마 설계는 진행) |
| **D** | 스코프를 좁혀서(성남 수정구+분당, "근린생활시설/상가"류 물건만) 저빈도 배치로 접근 — 활성 경매 물건 수 자체가 적을 것으로 추정 | 낮음~중간 | 스코프 밖 물건은 아예 안 잡힘(이 프로젝트 데이터축과 일치하니 허용 가능한 트레이드오프) | **채택 — B2와 결합** |

**채택(2026-07-19 갱신)**: 애초 B2(AJAX 역공학)+D를 채택했으나, 실제 브라우저(claude-in-chrome)로
직접 검색을 수행해보며 **B1(헤드리스 브라우저로 폼 조작)이 더 낫다는 쪽으로 뒤집힘**. 상세는 아래
"2026-07-19 실측 결과" 참고. B1+D로 최종 채택. 막히면 A(CODEF)로 폴백.

## 2026-07-19 실측 결과 — claude-in-chrome으로 직접 검증

**세션 계기**: CI/CD 러너 offline 문제(별개 이슈, 이 문서와 무관)로 대기하던 중, 사용자가 브라우저
확장을 연결해줘서 실제로 courtauction.go.kr을 조작해봄. `WebFetch`로는 빈 페이지만 반환됐던 것과
달리, 실브라우저는 WebSquare를 정상 렌더링함.

**시도 순서**: "매각예정물건" 검색 화면 → 소재지(지번주소) 방식으로 전환 → 시/도=경기도,
시/군/구=성남시 수정구, 용도 대분류=건물/중분류=상업용및업무용 지정 → 검색 클릭 → 결과 5건 확인 →
그중 하나(2025타경51795) 클릭해 상세페이지까지 진입.

**B2(AJAX 역공학)가 막힌 지점**: 개발자도구 네트워크 캡처로 `POST
.../pgj/pgjsearch/searchControllerMain.on`가 실제 검색 엔드포인트임을 확인했으나(다른 4개
`select*Lst.on` 호출은 드롭다운 옵션 목록용 보조 호출), 요청/응답 본문을 페이지 컨텍스트에
`fetch`/`XHR` 인터셉터를 심어 잡으려 하니 안 잡힘(아마 iframe 컨텍스트 분리 때문으로 추정) —
`iframe.src`를 직접 읽으려는 시도는 **claude-in-chrome 자체가 "쿠키/쿼리스트링 데이터로 판단해
차단"**함(세션 토큰 유출 방지용 안전장치로 보임). 즉 raw API 역공학은 세션 처리가 얽혀있어 계속
파고드는 게 이 안전장치와 계속 부딪힐 가능성이 높음.

**B1(헤드리스 브라우저로 실제 UI 조작)이 그냥 됨**: 폼 채우고 검색 버튼 누르고 렌더링된 텍스트를
읽는 것만으로 끝났음 — 세션/쿠키/AJAX 계약을 전혀 몰라도 됨. 그리고 상세페이지에서 나온 데이터가
예상보다 훨씬 풍부함:

- **목록 화면 필드**: 사건번호, 물건번호, 소재지 및 내역(지번주소+건물구조+면적), 비고(위반건축물 등
  경고문), 감정평가액, 담당계, 매각기일, 용도, 최저매각가격(할인율%), 진행상태(유찰 N회)
- **상세 화면 추가 필드**: 매수신청보증금, 입찰방법, 사건접수일/경매개시일/배당요구종기/청구금액,
  **기일내역 전체 이력**(과거 유찰된 회차별 매각기일+최저매각가격), 목록내역(층별 면적, 대지권
  비율), **감정평가요항표**(위치·교통·구조·이용상태·설비·토지형상·이용계획 서술형 텍스트, 심지어
  현재 임차인 상호명까지 — 예시 물건은 "커피에반하다"로 영업 중)

**실측 스코프 볼륨**: 성남시 수정구 + 상업용및업무용 필터만으로 **활성 물건 5건**(2026-07-19 기준,
예정매각기일 2026.08.03~09.17 구간). 접근 D(스코프 좁히기)의 가정이 실측으로 확인됨 — 이 정도
볼륨이면 헤드리스 브라우저 오버헤드는 전혀 문제가 안 됨.

**상세페이지는 SPA 내부 라우팅**(URL이 안 바뀌고 `#`만 붙음) — 즉 사건별 고정 URL로 직접
북마크·재요청이 안 됨. 매번 검색 폼부터 다시 조작해야 함(이건 B1을 어차피 헤드리스 브라우저로 폼을
끝까지 조작해야 한다는 뜻이기도 함 — B2로 "상세 API만 따로" 접근하는 우회도 안 통함).

## 채택 방향의 설계 스케치

### 왜 기존 LOCALDATA 패턴을 그대로 못 쓰나

지금까지 다룬 인허가 데이터는 **정적 스냅샷**(다운로드 한 번 받아 SQL로 변환해 git에 커밋, 서버 재시작마다
`data-locations`로 재로드)이다. 경매 물건은 **매일 상태가 바뀌는 라이브 데이터**(매각기일 연기, 유찰, 낙찰,
취하)라 이 패턴이 안 맞는다. 대신 H2가 서버 재시작마다 어차피 재구성되는 현재 구조를 그대로 활용해,
`@Scheduled` 배치가 주기적으로 최신 상태를 같은 H2 인스턴스에 upsert하는 방식으로 간다 — 시드 SQL 파일이
아니라 코드로 관리.

### 데이터 모델(2026-07-19 실측 반영, 여전히 초안)

- 신규 엔티티 `AuctionCase`: `site`와 N:1(하나의 PNU에 여러 차수/여러 물건번호가 있을 수 있음 — 실측
  사례 2025타경52088가 물건번호 1·2 두 개를 가진 것으로 확인). 필드(실측 화면 기준):
  사건번호, 법원, 물건번호, 물건종류, 감정평가액, 최저매각가격, 매수신청보증금, 입찰방법, 매각기일,
  담당계, 사건접수일, 경매개시일, 배당요구종기, 청구금액, 진행상태(유찰횟수), PNU(지번주소에서 도출).
- `AuctionScheduleHistory`(1:N, AuctionCase 하위) — 기일내역의 회차별 매각기일+최저매각가격+결과(유찰
  등). 실측 사례 하나가 이미 6회차 이력을 가짐.
- 감정평가요항표 서술 텍스트(위치·교통·구조·이용상태 등)는 자유 텍스트라 정형 컬럼화하지 않고
  `appraisalSummary` 같은 단일 텍스트 필드로 보존하는 편이 나을 듯(과도한 정형화 = YAGNI 위반).
- 노출 위치: 완전히 별개의 API가 아니라, 기존 `Tenancy` 타임라인 옆에 "경매이력"으로 곁들이는 방향
  (marketInfo처럼 Unit 상세 응답에 얹는 패턴과 유사) — 정확한 API 계약(`api-spec.md` 반영 여부)은
  다음 브레인스토밍에서 확정.

### 이번 문서가 못 끝낸 것 (다음 세션 착수 지점)

필드 스키마는 실측으로 확정됐지만(위 데이터 모델 참고), **실제 수집 코드(Java에서 헤드리스 브라우저로
같은 폼 조작을 재현하는 부분)는 아직 안 짬** — Playwright-Java 같은 라이브러리 도입이 필요한데
`pom.xml`에 아직 없음(신규 의존성 추가는 이번 문서 스코프 밖, 다음 설계에서 결정). 상세페이지가 SPA
내부 라우팅이라 매번 검색 폼부터 조작해야 하는 제약도 그 설계에 반영해야 함. `writing-plans`로 넘어가기
전에: (1) Playwright-Java 도입 여부 확정, (2) `AuctionCase`/`AuctionScheduleHistory`의 정확한 컬럼
타입·API 계약을 별도 브레인스토밍으로 확정, 이 두 가지가 선행 조건.

## 하지 않는 것 (명시적 스코프 제외, 이번 문서 기준)

- CODEF 계약 체결 — B2 실패 확인 전까지 보류.
- 헤드리스 브라우저 도입 — B2로 충분한지 먼저 확인.
- 성남 수정구+분당 외 지역 경매정보 — 프로젝트 데이터축과 일치시킴.
- 등기부등본 연동(권리분석) — 별도 스코프, 이번엔 손 안 댐.
